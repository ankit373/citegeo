# Known limitations and items still to verify

Applies to: the current `src/product` working tree, checked 2026-09-08, planned for release as **v0.2.0-rc.1, UNPUBLISHED**. What follows is source-code behavior and its gaps; it is not a claim that regression testing or container acceptance has run. A later fix should carry its own verification before this scope is updated.

## Release and real data

Phase 6's 20 cases have run to their final state, with actual raw text, failures, and screenshots archived independently. The budget cap is USD 2, covering preflight, failures, retries, and search. R02/R04's K runs include a JSON parsing failure; the runner finishing must never be written up as "every observation succeeded." Exact numbers are generated from the ledger and the case summaries; see this version's notes.

The actually-tested models are two offline routes, `openai/gpt-4o-mini` and `google/gemini-2.5-flash-lite`, and one web-enabled route, `openai/gpt-4.1-mini`. This round has real native metadata, K citations, and a due-scheduling record, but that does not mean every model and every route has been verified.

A historical Phase 5 acceptance report recorded `blocked`, an incomplete real K/scheduled call, and a missing budget at the time. That is a historical state; it must never be stretched into "still unauthorized today," and an old test's `passed` must never be used to declare this round `rc_ready`. Judging the release gate still needs the actual final state, a valid demo, the container/screenshots, and final frozen verification.

## Boundaries of measurement interpretation

What is published is this run's answer and its evidence; it does not expose the model's internal reasoning, and a rerun is not guaranteed to produce an identical answer.

- D has already named the domain, so a restated domain name must never be read as an organic-discovery rate; K is what observes an unprompted answer under a neutral keyword.
- A description, competitor, or associated keyword is the model's output for this run, not fact-checking, a business partnership, or a whole-market list. No keyword or no competitor does not mean it does not exist in reality.
- A provider citation, a search result, and a link in the answer are not equivalent; a citation does not prove the source is correct or that it had a causal effect.
- The current 20 domains are a targeted set of software products, and the cases are also in different languages; this must never be used for a random market statistic or a cross-language leaderboard.
- Three short-run observations do not guarantee statistical significance, long-term stability, or that an optimization worked; `temperature=0` does not guarantee an identical output.
- An API result is not the same as a result from a consumer web client like ChatGPT or Gemini. The OpenRouter route, the search mode, and the server-side configuration should always be disclosed.

## Statistics and evidence gaps

**L01: A first attempt and a retry result can get mixed.** [measurement-stats.ts](../src/product/measurements/measurement-stats.ts) selects `firstAttemptId`, but [measurement-store.ts](../src/product/measurements/measurement-store.ts)'s results/evidence are stored per probe and can be overwritten by a retry. Statistics can end up using the first run's `rawAnswer`/ID together with a later run's judgment/citations. A retry does not add to the probe count, but the current code cannot guarantee statistics always use only the first attempt's result.

**L02: A stats cache does not follow a result's status or a formula change.** A snapshot's ID includes only the run/probe/first-attempt ID; it does not incorporate completion status, the derived result, a citation hash, or the statistics version. Building a snapshot mid-flight, or rebuilding after a retry, can reuse stale content. The code also does not require the whole run to be in its final state; a probe that has not been written yet is not counted in that point's `planned`. A public figure should wait for the final state and recheck every sample.

**L03: Missing chart points and a keyword-grouping revision.** This round's recheck found the association chart mixing multiple keywords, affecting cases including R04. The association chart is now scoped to the current `keywordId`, with `keywordId` folded into the series identity, and a `null` point is kept as a genuine break; the chart's detail table also keeps its missing rows. This revision changes no raw answer or metric-point value. A separate synthetic browser regression was added covering "valid-null-valid" and mixed keywords; see the release checklist for final acceptance status — an old candidate's screenshot does not represent the new version.

**L04: A fingerprint does not cover every comparison condition.** A D fingerprint's `keywordSetHash` is `null`, so a change in the relative-weight denominator may not change the fingerprint; an object's alias/matching scope, the actual search path, the upstream model version, and the actual prompt/schema hash are also not fully folded into the fingerprint. The same fingerprint must never be treated as proof every condition is identical. A chart's horizontal axis shows observation points at equal spacing, not scaled to the real time span between them.

**L05: A D denominator allows `unknown` and a partial field recovery.** Only a nonexistent result or `analysis_failed` is excluded; `domainRecognition=unknown`/`null`, and a keyword field that is missing and falls back to an empty array, can still count toward the denominator. An association count shows `value=0` under a zero denominator, but with `pointState=no_data`. The denominator and any missing field must always be disclosed together; it must never be read as an already-well-observed zero.  See [measurement methodology](measurement-methodology.md) for the full formulas.

**L06: K's recommendation and first-position claims are not yet backed by mandatory text verification.** A judgment is taken directly from the model's own `recommendation` and `unique`/`tied` structured labels; a `null` or invalid `evidence` does not automatically exclude that sample, and the first offset is not used for an independent re-ranking either. An overall `completed` status makes all four judgments adjudicable, including an answer with `mentions=[]` or an unresolved first position. The user still needs to check the raw text.

This round's read-only audit actually found 7 conflicts across R06, R07, R10, R11, and R19 where more than one object claims a `unique` label; the related statistic points still read `0/1`. These points cannot prove the target was not mentioned or recommended first. All 8 positive-recommendation citation snippets trace back to the raw text verbatim, but a snippet existing does not resolve the first-position conflict. The machine record is at `validation/release-v0.2.0-rc.1/semantic-evidence-audit.json` locally.

**L07: Object mention and literal domain detection have limits.** `brand_name_mention` can be hit by an exact domain match alone; `domain_body_mention` is a case-sensitive `includes`, which can match inside a JSON field or a longer string, and its independent name/domain boundary is not verified. Identity matching accepts either the name or the domain matching, with no external identity verification.

**L08: Provider source classification and eligibility are not fully unified.** The recognition path requires `search.requested`, a title, and a payload path; the measurement path requires a payload path but can accept a missing title. Neither separately excludes `provider_search_result`. Measurement citation rate uses the requested `provider_native` configuration as web-enabled-denominator eligibility; it does not force a check of the actual `used` status, and it does not run the same citation-payload-path check a report does. So a search result, or unconfirmed search behavior, can be misread as a verified answer citation.

**L09: Recognition detail and a fixed report pick different revisions.** The detail page can prefer to show the latest AnalysisRevision; report building only takes `currentAttemptId`'s original archive. The latest revision might even come from a different, older attempt, so `sourceAttemptMap` must be checked; a re-analysis must never be assumed to have already synced to the report and the WatchSet suggestion.

**L10: A measurement's write order for raw text, and data completeness.** [measurement-service.ts](../src/product/measurements/measurement-service.ts) stores the result/evidence first, then stores the final-state attempt containing `rawAnswer`/`rawProviderResponse`. An interruption can leave a derived result with no raw text. `DomainProbeResult` does not fully store `fieldIssues` and per-competitor keywords, so a close recheck still needs the raw payload. A report's `safeProviderResponse` only checks that the JSON is serializable; it does not redact anything.

**L20: A native search's SDK path cannot be treated as the model's own built-in search.** The [OpenRouter search adapter](../src/providers/openrouter-native-search.ts) requests `engine=native`, but the actual metadata can come back `native`, `sdk`, or `unverified`; both SDK and native can map to `usedMode=provider_native`, and the interface's short label is not enough to tell them apart. `executionMode` and the raw `server_tools` metadata must always be disclosed. Built-in grounding's `alwaysOn` can also set `used=true` even when the execution confirmation is flagged `unverified`. Empty text is reported as `empty_answer` at the adapter stage, and tool/search metadata is not guaranteed to be archived alongside that failure. The combination of a JSON Schema and a required search tool needs a real preflight; the search/citation compatibility of all three tested model routes cannot currently be claimed as verified. See [evidence model](evidence-model.md) for detail.

## Scheduling, budget, and run recovery

**L11: The core budget and a case's budget are different things.** The core measurement service mainly checks that the initial planned count does not exceed `requestLimit`; `dailyRequestLimit` is checked against the task's ledger when it comes due, and `tokenLimit`/`costLimitUsd` do not form a per-request hard gate inside core execution. A manual measurement, an initial recognition, or an extra retry cannot rely on this alone to guarantee cumulative account cost stays under a cap. Scheduling reconciliation only sums each probe's latest cost, which can miss the cost of an earlier retry.

The Phase 6 case path has a separate StudyBudgetExecutor, wrapping the same real executor via an isolated product session: it reserves cost serially, persists a ledger for this phase, stops adding new calls when it hits `unknown_cost` or an over-reserved cumulative total, and sets provider HTTP attempts to 1. This round's paid calls already went through this path; it does not mean the default deployment's core server/worker carries the same cumulative-budget guarantee.

**L12: A task's bound scope can drift.** [schedule-service.ts](../src/product/scheduling/schedule-service.ts) stores `watchSetId` when a task is created; the due-check reads `activeBaselineId`, but dispatch calls the measurement service's current WatchSet. If the scope is swapped under the same baseline, the probes actually run can differ from the scope the task stored, and `plannedRequestCount`/the reserved cost can also go stale.

**L13: The skip/missed-time policy is not fully honored.** An early-return branch — overlap, budget block, or archived — does not advance the task; a repeated scan that finds an existing occurrence can get stuck on the original `nextRunAt`. Normal dispatch computes the next time from the original `scheduledFor`, so a long outage can end up catching up on old times one by one, rather than cleanly skipping the missed occurrences. It must never be claimed that "no backfill, no overlap, automatic recovery" is fully implemented today.

**L14: A run is not a persistent queue, and duplicate protection is not a global transaction.** The server creates a service instance per request, so a manual run's in-memory lock cannot serialize uniformly across requests/processes; the scheduling file lock isolates by task and cannot remove project-level concurrent contention between different tasks. A crash can leave a running attempt, a planned/started occurrence, or a lease-less lock behind. There is no recovery mechanism that guarantees exactly-once execution with automatic reclamation.

**L15: Archiving/deleting is not the same as canceling an in-flight request.** Archiving a project does not fully block a manual recognition/measurement from starting; a soft delete does not immediately stop an already-started async execution. Cleaning up a project should pause its tasks and let any in-flight request finish first, or a later write can still leave behind, or recreate, the project's subdirectory. Restoring an archived/deleted project should also recheck any leftover task and budget.

## Interface and deployment

**L16: Historical note — the UI is no longer bilingual.** *This note described an earlier state: the recognition/measurement pages carried hardcoded Simplified Chinese, and the measurement date display was fixed to `zh-CN`, independent of a run's own `zh`/`en` answer language. That Chinese-hardcoded UI, and the Chinese locale entirely, were removed after v0.2.0; the product and its documentation are English-only in this checkout, and the earlier caveat about the interface not being fully bilingual no longer applies.* The old Playwright configuration still hardcodes a macOS Chrome path; cross-platform testing should not be assumed to run out of the box.

**L17: Model and scope editing is limited.** The same model ID cannot be configured for both `off` and `provider_native` within one selection set. "Test only newly added models" is judged by whether a model ever appeared in the historical `modelScope`, without requiring that historical execution succeeded, so a model that failed before does not count as newly added. A new draft under an existing active WatchSet copies the prior scope and does not auto-absorb a new report's keywords; the core neutral-keyword filter is only an identity-substring exclusion, and cannot guarantee every keyword is a good fit for neutral selection.

**L18: Boundaries of the local file service.** There is currently no login, access control, TLS, multi-tenant authorization, or a full path-security audit; the project-ID/parent check is a data-organization check, not tenant isolation for a public deployment. There is no arbitrary SPA path fallback; page entry points are the root path and query parameters. A single-file atomic write does not provide a database-level transaction, a cross-process snapshot, or encrypted/tamper-evident storage.

**L19: The candidate is not yet publicly released.** rc4 already uses the current product server, includes the new SVGs, mounts a full `product-v2`, and has completed a two-architecture run, an independent backup read, and a rollback read of the previous local candidate; all 53 product screenshots correspond to the same candidate digest. A public registry pull, a site deployment, and an independent release commit remain unverified. See the version notes for the exact record. There is no automatic legacy migration; do not run the old CLI and treat old data as a result of the new protocol.

## How this is handled and reported

Keep the raw attempts, tasks, costs, and old snapshots that a known issue involves, rather than masking a gap by swapping in replacement data. A public figure should carry its actual samples and sources; a metric that cannot be rechecked is marked "needs recheck"; verification that has not run is stated plainly as unverified. After a fix, add verification for the affected boundary and update [architecture](ARCHITECTURE.md), [methodology](measurement-methodology.md), [evidence](evidence-model.md), and the release record to match.
