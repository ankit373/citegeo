# CiteGEO audit execution boundary design

## 1. Goal

A formal CiteGEO audit does exactly three things:

1. Submit the user's confirmed questions to the target provider verbatim.
2. Store the provider's actual answer, its native search status, and its citations.
3. Once the answer is safely stored, generate analysis and a report that can degrade but can never destroy the raw result.

Site pre-analysis, question suggestion, and brand profiling belong to the preparation stage. They can help the user prepare the audit, but they cannot decide whether a formal audit is allowed to run, and they must never hand the target site's content to the model under test.

## 2. Inviolable system constraints

- No regular expression literal and no `RegExp` constructor, anywhere.
- No branch dedicated to a specific brand, domain, language, model, industry, or test case.
- No error-type decision based on error message text; every error must come from a structured error code.
- The execution plan is generated by deterministic code from the confirmed domain, brand, questions, models, language, and search-mode settings.
- A site crawl failure must never block a formal provider request.
- Site body text, SEO fields, README content, and profiling results must never enter a formal provider question.
- A non-empty provider answer must be persisted before any analysis runs on it.
- A later analysis failure must never rewrite a provider success into a provider failure.
- "AI does not recognize the brand," a wrong answer, no citations, and no search results are all valid observations.
- Test expected values belong only to the validator; they must never enter a provider request or the business analysis context.

## 3. Three mutually isolated pipelines

### 3.1 Preparation pipeline

```text
Domain
-> Attempt to crawl the public site
-> Optional structured brand profile
-> Generate brand, alias, keyword, and question suggestions
-> User confirmation
```

The output is `PreparationResult`. A preparation failure can only produce `unavailable`; it must never throw a business exception that blocks the formal audit.

### 3.2 Formal audit pipeline

```text
ConfirmedAuditSpec
-> QuestionAdmission
-> DeterministicPlanBuilder
-> Create Run and Observation placeholder records
-> Call the target provider
-> Persist the raw answer immediately
```

This pipeline must never import the site-evidence module, the brand-profiling module, the prompt generator, or the LLM classifier.

### 3.3 Post-processing analysis pipeline

```text
Persisted ProviderAnswer
-> Intent and task analysis
-> Brand, candidate, recommendation, and entity analysis
-> Citation classification
-> Report model
-> HTML / Markdown / JSON
```

Post-processing analysis may fail or partially complete, but it must preserve the formal answer and produce a degraded report.

## 4. Core objects

### 4.1 User-confirmed input

```ts
interface ConfirmedAuditSpec {
  projectId: string;
  domain: string;
  target: {
    name: string;
    aliases: string[];
  };
  questions: ConfirmedQuestion[];
  providerTargets: ProviderTarget[];
  language: string;
  runCountPerQuestion: number;
  scopeConfirmed: true;
}

interface ConfirmedQuestion {
  id: string;
  text: string;
  enabled: boolean;
  declaredIntents: BrandQuestionIntent[] | null;
}
```

`declaredIntents` is metadata the user explicitly chose, or that a confirmed question already carries. When absent it is stored as `null`; an LLM must never be called before the formal audit just to fill it in.

### 4.2 Site preparation result

```ts
interface PreparationResult {
  status: "available" | "unavailable";
  domain: string;
  profile: SuggestedBrandProfile | null;
  evidence: SitePreparationEvidence[];
  failure: PreparationFailure | null;
  providerCalls: string[];
}
```

`PreparationResult` is not part of `ConfirmedAuditPlan`'s execution context. A project may store it for the user to review later, but `AuditExecutor` does not accept this type as a parameter.

### 4.3 Deterministic run plan

```ts
interface ConfirmedAuditPlan {
  id: string;
  projectId: string;
  target: Entity;
  prompts: MonitoringPrompt[];
  providerTargets: ProviderTarget[];
  language: string;
  runCountPerPrompt: number;
  promptSetHash: string;
  plannedObservationCount: number;
  createdAt: string;
}
```

`DeterministicPlanBuilder.build(spec)` is a pure function. The same input must always produce the same prompt set, provider targets, and comparability hash. The plan ID and creation time are supplied by an outer factory, so the pure function never depends on the current time internally.

### 4.4 Site status kept separate from AI results

```ts
interface ObservationExecution {
  sitePreparationStatus: "available" | "unavailable" | "not_requested";
  providerAnswerStatus: "pending" | "completed" | "empty" | "failed";
  providerSearchUsed: boolean;
  providerSearchMode: "none" | "provider_native" | "provider_always_on" | "unverified";
  brandRecognition: "recognized" | "not_recognized" | "unclear" | null;
  providerCitations: Citation[];
  rawAnswer: AnswerResult | null;
  analysisStatus: "pending" | "completed" | "partial" | "failed";
  reportStatus: "pending" | "completed" | "degraded" | "failed";
}
```

`null` only means "not yet run" or "nothing was generated." `false`, `not_recognized`, and an empty citation array are all genuine results of a completed run.

## 5. Deterministic admission

### 5.1 Identity check

The identity check does only a deterministic text-containment test:

1. Run Unicode `NFKC` normalization on the question and the confirmed identity anchors.
2. Apply language-neutral case folding.
3. Use a plain string `includes` check for the brand name, the normalized domain, or a user-confirmed alias.
4. No tokenization rules, no keyword lists, no regex, no language-specific handling.

### 5.2 Product relevance

Code must never decide semantic relevance from industry keywords. Relevance is expressed by a user confirmation action instead:

- In the UI, the user sets `scopeConfirmed: true` after completing the question-confirmation step.
- In the API and CLI, the caller must explicitly submit a confirmation flag.
- The frozen regression manifest has the suite declare that its questions were manually confirmed.
- An unconfirmed question returns `scope_confirmation_required` and never calls the provider.

This keeps the product boundary that "a question must be directly related to the target brand" without introducing a language word list, brand rules, or a fragile upstream LLM-JSON pass.

## 6. Execution state machine

```text
spec_received
-> admission_passed
-> plan_created
-> run_created
-> provider_request_started
-> provider_answer_persisted
-> analysis_started
-> analysis_completed | analysis_partial | analysis_failed
-> report_completed | report_degraded
```

Every state can only move forward. A later step failing must never roll back or delete data that was already persisted earlier.

### Write order

1. Create the `Run`.
2. Create an `Observation` placeholder record for every question and model.
3. As soon as the provider responds, write the raw request, raw response, answer text, citations, search status, tokens, cost, and timestamps.
4. Mark `providerAnswerStatus`.
5. Run analysis separately, writing its results incrementally.
6. Generate a full or degraded report from whatever fields are currently available.

The report quality gate must never wrap around raw-answer storage. The quality gate can only decide whether the report is `completed` or `degraded`.

## 7. Structured AI output gateway

Every post-processing task that needs structured output goes through `StructuredAnalysisGateway`:

```ts
interface StructuredAnalysisGateway {
  run<T>(request: {
    purpose: AnalysisPurpose;
    schemaName: string;
    schema: JsonSchema;
    input: unknown;
    validate: (value: unknown) => ValidationResult<T>;
  }): Promise<StructuredAnalysisResult<T>>;
}
```

Rules:

1. The first request must carry a JSON Schema.
2. When the provider does not support Schema, that capability is flagged `unsupported`; it must never silently fall back to free-text JSON.
3. When a Schema response fails to parse or validate, exactly one structured repair request is allowed.
4. The repair request still carries the same Schema, and receives only the previous raw output plus the validation error structure.
5. After a second failure, return `analysis_failed`; never throw an exception that would lose the answer.
6. A missing field is represented as `null`, `unknown`, or an empty array; unknown must never be disguised as a negative conclusion.

Repair logic never guesses at JSON via string slicing, and never makes a decision by checking whether an error message contains a substring.

## 8. Provider boundary

The provider interface is split:

```ts
interface AnswerProvider {
  answer(input: AuditAnswerRequest): Promise<ProviderAnswerOutcome>;
}

interface StructuredProvider {
  structured<T>(input: StructuredRequest<T>): Promise<StructuredOutcome<T>>;
}
```

A formal question only goes through `answer()`. Site preparation and post-processing analysis can only reach the provider gateway through their own explicit call purpose.

`AuditAnswerRequest` may only contain:

- the user-confirmed question;
- the answer language;
- the model;
- the maximum output length;
- whether provider-native search is enabled.

The type carries no field for site body text, SEO data, README content, a competitor profile, or a suggested question, ruling out injection at the compilation boundary.

## 9. Error model and retries

Every provider adapter returns a structured failure:

```ts
type ProviderFailureCode =
  | "authentication"
  | "billing"
  | "rate_limited"
  | "timeout"
  | "upstream_unavailable"
  | "unsupported_capability"
  | "empty_answer"
  | "invalid_response"
  | "unknown";
```

Retry policy is decided by error code, never by reading error message text:

- `rate_limited`, `timeout`, `upstream_unavailable` can retry under the shared policy.
- `empty_answer` can retry after raising the output limit.
- `authentication`, `billing`, `unsupported_capability` never retry.
- Every retry is written to the call ledger as its own independent call.

A site crawl also returns a structured `PreparationFailureCode`, but no matter the failure type, it never blocks a confirmed audit.

## 10. Call and cost ledger

Every model call must go through `MeteredProviderGateway`:

```ts
type ProviderCallPurpose =
  | "site_preparation"
  | "prompt_generation"
  | "question_classification"
  | "audit_answer"
  | "answer_analysis"
  | "report_analysis"
  | "structured_repair";

interface ProviderCallLedgerEntry {
  id: string;
  parentCallId: string | null;
  projectId: string | null;
  runId: string | null;
  observationId: string | null;
  purpose: ProviderCallPurpose;
  providerId: string;
  model: string;
  startedAt: string;
  finishedAt: string;
  outcome: "completed" | "empty" | "failed";
  inputTokens: number | null;
  outputTokens: number | null;
  costUsd: number | null;
  failureCode: ProviderFailureCode | null;
}
```

Test reports count calls, successes, retries, tokens, and cost separately per `purpose`. `auditCalls` counts only `purpose === "audit_answer"`, never inferred backward from whether a report exists or from string logs.

## 11. Three entry points share one execution core

### Interactive project

```text
Optional SitePreparationService
-> User confirms ConfirmedAuditSpec
-> DeterministicPlanBuilder
-> AuditExecutor
```

### Scheduled monitoring

```text
ActiveBaseline
-> ConfirmedAuditSpecAdapter
-> DeterministicPlanBuilder
-> AuditExecutor
```

### Frozen regression test

```text
FrozenManifestCase
-> ValidationCaseAdapter
-> ConfirmedAuditSpec
-> DeterministicPlanBuilder
-> AuditExecutor
```

The three entry points may differ only at the spec-adaptation stage. The formal plan and the executor are fully shared, and `src` must never branch on a case ID, a domain, or a brand.

`expectedIntents` stays inside the validator's `oracle`; it is never passed to the provider and never written into post-processing analysis input. The validator uses it to check an independently produced analysis result, so the test's expected answer never leaks into the system ahead of time.

## 12. Module layout

```text
src/preparation/
  preparation-schema.ts
  site-preparation-service.ts

src/admission/
  question-admission.ts
  admission-schema.ts

src/planning/
  confirmed-audit-spec.ts
  deterministic-plan-builder.ts

src/execution/
  audit-executor.ts
  observation-recorder.ts
  execution-state.ts

src/structured/
  structured-analysis-gateway.ts
  schema-validation.ts

src/telemetry/
  provider-call-ledger.ts
  metered-provider-gateway.ts

src/validation/
  validation-case-adapter.ts
  validation-oracle.ts
```

Responsibility migration for existing modules:

- `DomainProfiler` and `SiteEvidenceCollector` move entirely into `preparation`.
- `AuditPlanner` is split, with deterministic plan-building pulled out; LLM prompt generation stays as a pre-confirmation suggestion capability.
- `AuditRunner` keeps only execution orchestration and no longer implicitly calls the planner.
- `IntentResultPipeline` moves into post-processing analysis and returns a failure status instead of breaking the run.
- `FileStore` gains incremental writes and no longer waits for the whole report before saving once.

## 13. Implementation tasks

### Stage A: establish the boundary

1. Add the `ConfirmedAuditSpec`, `PreparationResult`, `ProviderAnswerOutcome`, and call-ledger types.
2. Implement deterministic `QuestionAdmission` and `DeterministicPlanBuilder`.
3. Require `AuditRunner` to receive an already-confirmed plan; remove implicit recursive planning.
4. Move site preparation out of the formal execution dependency graph.

### Stage B: persist the answer first

5. Create `Run` and `Observation` placeholder records.
6. Persist the raw result incrementally as soon as the provider responds.
7. Turn response analysis, competitor discovery, intent analysis, and report building into post-processing steps.
8. Add a degraded report so a non-empty answer is always paired with a report.

### Stage C: structured output and cost

9. Add the unified JSON Schema gateway and a single structured repair pass.
10. Remove the free-text JSON fallback and JSON-container guessing.
11. Replace error-message matching with error codes returned by provider adapters.
12. Wire every provider call into the phased ledger.

### Stage D: validation entry point

13. Rewrite the real-suite entry point to build `ConfirmedAuditSpec` directly from the manifest.
14. Move `expectedIntents` into the validation oracle, keeping it out of the flow under test.
15. Store the code hash, manifest hash, per-stage call record, and per-case state machine.
16. Confirm the validation output directory is fully isolated from the user's project directory.

### Stage E: static constraints against shortcuts

17. Use a TypeScript AST check to confirm no regex literal and no `RegExp` construction exists in production code.
18. Use AST and manifest data to confirm no test-brand, test-domain, or case-ID literal exists in `src`.
19. Check the execution module's import graph to forbid a dependency on preparation, keyword collection, or prompt generation modules.
20. Check formal provider request snapshots to confirm they contain no site body text, SEO data, README content, or preparation results.

## 14. Test order and closing rules

The frozen real suite is not run while code is being changed. Once code meets the static and unit test bar, freeze the code, then run in this order:

1. A single-case `case-31` smoke test.
2. A three-case smoke test: `case-31`, `case-34`, `case-41`.
3. A full run of the unmodified 20-case manifest.

Every round records its code hash and manifest hash. Once a real test starts, code, manifest, questions, models, and expected values must not change. Even if the first few cases fail, that round must still run to completion and save its full JSON report. Only once a round has finished may code be changed based on the report, starting an entirely new round.

Every case must output:

```json
{
  "admission": {},
  "plan": {},
  "project": {},
  "run": {},
  "providerAnswer": {},
  "analysis": {},
  "report": {},
  "providerCallsByPurpose": {},
  "artifacts": {},
  "checks": {}
}
```

## 15. Completion criteria

- All 20 cases produce a deterministic plan and a project-isolated record.
- All 20 cases actually produce an `audit_answer` call.
- No upstream plan-JSON parse failure exists.
- A site preparation failure never blocks a formal answer.
- No site preparation content exists in a formal request.
- A provider's non-empty answer is persisted before post-processing analysis runs.
- An analysis failure still produces a degraded report that contains the raw answer.
- "Not recognized," "no citations," and a wrong answer can all be presented as genuine results.
- Call counts and cost can be checked item by item, per phase.
- No regular expression exists in code or test scripts.
- No brand-, domain-, language-, or case-specific logic exists in production code.
